# Testing

Desktop-only native test suite (`test/native/`), following
[TinyMPG](https://github.com/pschatzmann/TinyMPG)/[TinyH264](https://github.com/pschatzmann/TinyH264)'s
exact approach: each `test_*.cpp` is a standalone executable, and the
three that touch real image data (`test_decode_gradient`,
`test_decode_checker420`, `test_decode_grayscale`) decode a real
libjpeg-encoded JPEG and check the result against
[Pillow](https://python-pillow.org/)'s own decode of the same file (Pillow
wraps libjpeg) - this project's correctness oracle, not
conformance-suite guesswork, the same role `ffmpeg` plays for
TinyMPG/TinyH264's own decode tests. None of this runs on an embedded
target; it's a host-only (native g++/clang/MSVC) build against the same
headers `examples/` use.

```sh
mkdir build && cd build
cmake ..
make
ctest --output-on-failure
```

Or, as a CMake subproject from a parent build: `add_subdirectory(TinyJPEG)`
then `target_link_libraries(your_target PRIVATE TinyJPEG)`.

For ESP-IDF: reference this directory via `EXTRA_COMPONENT_DIRS` (the
top-level `CMakeLists.txt` already handles the `ESP_PLATFORM` branch via
`idf_component_register()`).

## Why pixel comparisons are tolerance-based, not byte-exact

Two independent sources of difference, both expected, neither a bug:

1. **RGB565 quantization.** `TinyJPEGDecoder`'s callback delivers RGB565
   (16-bit, 5-6-5) by default; the oracle comparison is against Pillow's
   full RGB888 decode. Packing 8-bit R/G/B down to 5/6/5 bits alone
   accounts for a few units of per-channel difference - see
   `test_decode_grayscale.cpp`'s file comment for a worked example of why
   even a perfectly gray pixel doesn't round-trip through RGB565 as an
   exact R==G==B.
2. **Independent rounding.** libjpeg's and tjpgd's IDCT/color-conversion
   implementations are both spec-legal but not bit-identical, so a handful
   of samples landing a few units apart from Pillow's particular rounding
   is expected on real content, the same underlying reason TinyMPG's own
   `test_decode_iframe.cpp` gives for *its* tolerance-based bound.

`test_decode_gradient.cpp` (a smooth, low-frequency 4:4:4 - unsubsampled
chroma - gradient) uses a tight bound calibrated to those two sources
alone: mean sum-of-|ΔR|+|ΔG|+|ΔB| per pixel ≤ 20, max ≤ 40.
`test_decode_checker420.cpp` (a deliberately adversarial 8px checkerboard,
4:2:0 subsampled) uses a much looser bound (mean ≤ 70, max ≤ 200) for a
third reason that's about the *content*, not the decoder: sharp,
high-contrast edges aligned to the 8x8 DCT block grid are a worst case for
lossy JPEG compression, producing real ringing artifacts that both
decoders reproduce (each decodes the same DCT coefficients), but not
identically down to the last unit. That test's own file comment has the
full reasoning, including how the result was visually confirmed correct
(no shifted/duplicated/garbled blocks - the specific failure mode that
asset exists to catch, since it's the one test image big enough to need
more than one MCU column and exercise 4:2:0's doubled-block-width/height
path in `tjpgd_detail::mcu_output()`) before its numeric bound was set.

## How test assets are generated

`test/native/assets/*.jpg` (input) and `*.ppm`/`*.pgm` (oracle decode
output) are generated by a small Python/Pillow script - regenerate them
with it if the test images ever need to change, rather than hand-editing
the binary assets:

```sh
python3 test/native/gen_assets.py
```

See that script for the exact parameters (size, JPEG quality, chroma
subsampling) behind each asset.

## Test list

Mirroring TinyMPG/TinyH264's explicit-list-not-glob convention in
`test/native/CMakeLists.txt` (a glob silently misses newly-added test
files without a manual re-configure):

- `test_decode_gradient` - decode of a smooth 4:4:4 (unsubsampled) 64x48
  gradient vs. Pillow's own decode - the core correctness gate for the
  common/simple case. Tolerance-based, not byte-exact - see above.
- `test_decode_checker420` - decode of an adversarial 4:2:0 (subsampled)
  64x48 checkerboard vs. Pillow's own decode - the core correctness gate
  for chroma subsampling and the doubled-block-width/height MCU assembly
  path 4:4:4 never exercises. Much looser tolerance than
  `test_decode_gradient` - see above for why.
- `test_decode_grayscale` - decode of a single-component (monochrome)
  source image vs. Pillow's own decode - exercises `mcu_load()`'s
  "synthesize flat chroma" path for a grayscale source, still through the
  default RGB565 output format.
- `test_get_size` - `getJpgSize()` reports correct dimensions from just
  the header (no `setCallback()` even registered) across every asset, and
  zeroes `*w`/`*h` on failure rather than leaving a caller's prior values.
- `test_scale` - `setJpgScale(1|2|4|8)` produces output divided by that
  factor; an unrecognized factor falls back to 1 (full size); the `x`/`y`
  offset passed to `drawJpg()` is added on top of the (already-scaled)
  block coordinates.
- `test_error_handling` - empty input, non-JPEG garbage, and a real JPEG
  truncated before its scan data must all fail cleanly with a `JRESULT !=
  JDR_OK` and never invoke the block callback; a callback that returns
  `false` must surface as `JDR_INTR`.
- `test_file_source` - the templated `drawJpg(x, y, FileT&)`/
  `getJpgSize(w, h, FileT&)` overloads, driven by a from-scratch stdio
  `FILE*`-wrapping `FileT` (standing in for what would be Arduino's
  `fs::File`/SD's `File` on-device - see `docs/decoding.md` for the exact
  contract), checked pixel-for-pixel against the plain array overload on
  the same bytes.
- `test_callback_source` - the plain-function-pointer
  `drawJpg(x, y, InputCallback, void*)` overload, driven through many
  small reads rather than one big buffer handed over up front, checked
  pixel-for-pixel against the plain array overload - see that test's file
  comment for the exact read-fulfillment contract this exercises.
- `test_multiple_instances` - two `TinyJPEGDecoder` instances, configured
  differently (scale, userData) but sharing the very same callback
  function, used interleaved, must not perturb each other - the property
  that wouldn't have held for TJpg_Decoder's original singleton design
  (see `docs/architecture.md`'s "No more singleton" and "The callback's
  `decoder` parameter and setUserData()" sections).
- `test_encode_roundtrip` - the main correctness gate for the *encoder*
  (`tjpge.h`): encode a synthetic gradient (RGB 4:4:4, RGB 4:2:0, and
  grayscale) with `je_prepare()`/`je_encode()`, decode the result back
  with this same repo's `tjpgd.h` (via `TinyJPEGDecoder`), and diff
  against the original source pixels - see `docs/architecture.md`'s
  "Encoder" section for why this (rather than comparing against an
  external oracle like the decode tests do) is the right check here: it
  validates against a decoder already proven correct against libjpeg, so
  a pass means the encoder produced a spec-legal bitstream a conformant
  decoder reads back faithfully. Tolerance-based per-mode bounds, measured
  (not guessed) on the exact synthetic asset generated in the test itself
  - see that file's own comments for the numbers and what dominates each
  bound (RGB565 quantization, chroma-subsampling error, independent
  forward/inverse-DCT rounding).
- `test_encoder_wrapper` - `TinyJPEGEncoder`'s three output sinks (fixed
  array, a from-scratch stdio `FILE*`-wrapping `FileT`, and a plain
  callback) must all produce byte-identical output for the same input;
  an array sink smaller than the encoded output must fail with
  `JER_INTR` rather than silently truncating; `setUserData()`/
  `getUserData()` round-trip. Doesn't re-check bitstream correctness
  (that's `test_encode_roundtrip`'s job) - just that the wrapper's
  sink-selection plumbing doesn't alter what `tjpge.h` produces.
- `test_encode_rgb565` - `JE_FMT_RGB565` input specifically: encodes a
  synthetic RGB565 (5-6-5 packed) gradient and decodes it back, comparing
  against the *RGB565-quantized* reference (each channel's 5/6/5 bits
  expanded back up to 8, the same expansion `tjpge_detail::get_rgb()`
  itself performs) rather than a full-precision RGB888 source - see that
  file's own comment for why: RGB565 input is lossy before the encoder
  ever sees it, and comparing against the already-quantized reference
  isolates the JPEG-specific error from that unrelated, expected loss.
- `test_encode_rgb666` - `JE_FMT_RGB666` input specifically: since this
  format is handled byte-identically to `JE_FMT_RGB888` in `get_rgb()`
  (no bit expansion needed, unlike RGB565), this test's job is proving
  `je_prepare()`/`encodeJpg()` actually accept the new enum value (not
  `JER_PAR`) and derive `ncomp==3` for it correctly, then round-trip
  against the 6-bit-quantized source buffer itself as the reference.
- `test_encode_streaming` - the row-band streaming API
  (`je_start()`/`je_write_rows()`/`je_finish()` in `tjpge.h`): encodes a
  70x45 image (deliberately not a multiple of 8 or 16 in either
  dimension, to exercise both the existing right-edge column padding and
  the new bottom-edge row padding `je_finish()` adds) three ways - one
  `je_encode()` call, `je_write_rows()` fed 1 row at a time, and fed 7
  rows at a time (divides neither the 8- nor 16-row band size) - and
  asserts all three produce byte-identical compressed output, for both
  subsampling modes. Also round-trips the result through the decoder, and
  checks the streaming API's call-order/row-count error contract
  (`JER_PAR` for writing before `je_start()`, double-starting, exceeding
  `height`, writing after `je_finish()`, finishing early, double-finishing).
- `test_encoder_wrapper_streaming` - the wrapper-level counterpart:
  `TinyJPEGEncoder::beginEncode()`/`writeRows()`/`finishEncode()`,
  checked against `encodeJpg()`'s full-buffer output for byte-identical
  results on the array and callback sinks, run back-to-back with
  `encodeJpg()` on the *same* instance to prove the two APIs sharing
  `workspace_` don't leave stale state behind for each other.
